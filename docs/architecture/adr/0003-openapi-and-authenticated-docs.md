# ADR 0003: Contractual Parity and Perimeter Security

## Status

Accepted, and **not implemented as written**. Corrected 2026-08-28; the decision
below is left standing so the gap between it and the code is legible.

Three of its claims are false in the current tree, and each was verified rather
than inferred:

1. **`docs/api/openapi.yaml` is not the served contract.** The binary serves a
   swaggo-generated **Swagger 2.0** document from `services/feedback/docs/docs.go`
   (`// Code generated by swaggo/swag. DO NOT EDIT`), wired in through the blank
   import in `cmd/api/main.go` and `v1.GET("/swagger/*any", ...)`. Repository-wide,
   `docs/api/openapi.yaml` has **no references outside prose** — nothing reads it,
   builds from it, or validates against it.
2. **Generation is not automated.** There is no `swag init`, no `go:generate`, and
   no schema tooling in any workflow, Makefile, Dockerfile or package.json. The
   served document is regenerated by hand, off-repo.
3. **Propagation is not atomic, and has already failed.** `openapi.yaml` was
   edited on 2026-08-28 while `docs.go` and the handler had not moved since
   2026-04-11: the most recently edited contract is the one nothing reads. The
   three documents that exist, `openapi.yaml`, `docs.go` and
   `shared/contract/README.md`, agree on no complete endpoint. 429 is reachable
   on every route and appears in none of them; 413 appears only in the README and
   is not actually returned; the base URL has four different values, none of which
   is the one the clients use.

What is true: the X-API-Key perimeter exists and is enforced
(`internal/auth/middleware.go`), including on the Swagger route.

**Until a generation step exists, treat `docs.go` as authoritative** because it is
what callers receive, and treat the other two as documentation that may be wrong.
Choosing which document is real, and wiring generation to it, is the decision this
ADR still owes.

## Context

The MonOCR feedback service exposes endpoints for mobile character contributions and error reporting. To maintain production stability, the service requires machine-readable API specifications to ensure client-server parity and mitigation of unauthorized access to linguistic asset ingestion pipelines.

## Decision

Implementation of a dual-layer documentation and security strategy:

1. **Machine-Readable Specification**: A formal `openapi.yaml` contract for design-time enforcement.
2. **Authenticated Interactive UI**: A Swagger UI served via the Go binary, restricted behind the same **X-API-Key** middleware used for production endpoints.

## Rationale

- **Contractual Parity**: Automated generation of documentation ensures that mobile clients (Android/iOS) adhere to the standardized JSON schema, reducing integration entropy.
- **Access Perimeter**: The feedback service is a restricted-access utility. X-API-Key enforcement establishes a basic security perimeter suitable for native mobile ingestion, ensuring that even documentation reflects the project's security posture.
- **Idempotency and Validation**: The specification mandates strict MIME-type and payload constraints, ensuring that only authenticated, valid linguistic assets traverse the ingestion pipeline.

## Alternatives Considered

- **OIDC/OAuth2**: Rejected as disproportionate for a specialized, community-driven ingestion utility; X-API-Key provides sufficient isolation for the current deployment phase.

## Audit Constraints

- **Key Rotation**: Infrastructure procedures must exist for secure credential rotation.
- **Schema Drift**: Any structural changes to the Go ingestion logic must be propagated atomically to the `openapi.yaml` contract. **This constraint has no mechanism and has already been violated** — see Status. A constraint with nothing enforcing it is a wish, and this one cost the project three contracts that disagree.
